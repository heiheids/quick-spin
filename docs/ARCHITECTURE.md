## 3. 渲染管线：不闪烁、不拖影

这是本项目的**核心质量约束**，所有设计围绕它展开。

### 3.1 合成链路

```
D3D11 Device ──► DXGI Flip SwapChain (B8G8R8A8, PREMULTIPLIED, BufferCount=2)
                        │
                        ▼
              D2D1 DeviceContext  ── 绘制全部内容
                        │
                        ▼
        IDCompositionVisual ──► IDCompositionTarget ──► HWND
                        │
                        ▼
                 DWM 合成 + 系统亚克力模糊
```

窗口使用 `WS_EX_NOREDIRECTIONBITMAP`：**没有重定向位图**，GDI 完全不参与窗口绘制，
从根上消除"擦背景 → 重画"的闪烁路径。窗口内容全部由 DComp 提交，DWM 负责最终合成与模糊。

### 3.2 七条铁律

| # | 禁止 | 必须 | 原因 |
|---|---|---|---|
| 1 | 用 `SetWindowPos` 手动跟鼠标拖动窗口 | `WM_NCHITTEST` 返回 `HTCAPTION`，交给系统拖 | 手动拖是**拖影的头号成因**：鼠标位置与窗口位置不同步 |
| 2 | 用 `WS_EX_LAYERED` + `UpdateLayeredWindow` | DComp 提交视觉 | 分层窗口每次拖动要 CPU 拷贝整张位图，必然掉帧/残影 |
| 3 | 默认处理 `WM_ERASEBKGND` | 直接 `return 1` | 系统擦背景 = 白闪一帧 |
| 4 | 每帧无条件重绘 | 按需重绘：状态变了才 `Present` | 无动画前提下，空闲时 CPU 应为 0 |
| 5 | `WM_SIZE` 时销毁重建 D3D 设备 | 只 `ResizeBuffers` | 重建设备要上百毫秒，缩放过程会明显卡顿 |
| 6 | 缩放中跳过内容绘制 | 拖动全程完整重绘 | ~~轻量模式~~已废弃：见下方 2026-10-17 修订 |
| 7 | 只在自家消息循环里绘制 | `WM_PAINT` 里 `ValidateRect` 后**立即绘制** | 模态尺寸循环期间消息循环被阻塞，只有 `WM_PAINT` 能画出来 |

### 3.3 重绘驱动

> **2026-10-17 修订（铁律 6、7）**
>
> 原方案是"拖动尺寸时进轻量模式只画面板"+"绘制只在自家消息循环里做"。
> 实测发现这会导致**拖动过程中画面完全不更新**：窗口看着移动了却没变大，
> 缩小时描边被裁掉，松开鼠标才刷新。
>
> 根因：拖动边框时 Windows 会进入**模态尺寸循环**，该循环是从
> `DefWindowProcW(WM_NCLBUTTONDOWN)` 内部启动的 —— 也就是说我们自己的
> 消息循环此刻正阻塞在 `DispatchMessageW` 里。于是：
>
> * `WM_SIZE` 照常派发 → 交换链重建、布局重算都正确执行
> * 但**绘制语句永远等不到执行**，因为它只写在那个被阻塞的循环里
> * `WM_PAINT` 当时只做 `ValidateRect`，不画任何东西
>
> 因此改为：`WM_SIZE` 里主动 `InvalidateRect` 请求重绘，`WM_PAINT` 里
> `ValidateRect` 之后**立即绘制**。`take_dirty` 会消费脏标记，所以不会与
> 消息循环里的那次绘制重复，也就不会形成重绘风暴（原铁律 7 担心的正是这个）。
>
> 同时废弃轻量模式：拖动时跳过内容绘制，用户看到的是"内容停在旧尺寸"，
> 主观上比掉几帧更像卡死。Present 的垂直同步已把频率限制在刷新率。
> `resizing` 标志改用于选择 Present 的同步间隔（拖动时不等垂直同步）。

无动画 ⇒ 采用**脏标记 + 单次提交**模型：

```
输入消息 / 定时器 / IO 回调
        │
        ▼
   app::Event  ──►  修改 UiState  ──►  mark_dirty(区域)
                                            │
                                            ▼
                              消息循环空闲时：BeginDraw → 重绘脏区 → EndDraw → Present
```

绘制列表（文字、图元）只在**失效时重建**，不在每帧重建。
这样 `i18n` 查表、布局计算都只在需要时发生，空闲时整个程序不耗 CPU。

## 5. 配置与运行时状态分离

TOML 写入会**丢失注释**。若程序把窗口尺寸之类的运行时数据写回 `config.toml`，
用户精心写的注释会被冲掉。因此拆成两个文件：

| 文件 | 归属 | 内容 | 程序是否写入 |
|---|---|---|---|
| `%APPDATA%\QuickSpin\config.toml` | **用户** | 配色、布局、来源、热键、语言 | 仅首次生成。之后只在用户于设置面板点"保存为默认"时写 |
| `%APPDATA%\QuickSpin\state.toml` | **程序** | 窗口尺寸/位置、当前选项卡、图标尺寸、当前配色方案名 | 每次状态变化后延迟写 |

设置面板里的调整默认落在 `state.toml`（即时生效、重启保留、不碰用户注释）；
需要固化为默认值时才显式写回 `config.toml`。

## 6. 无边框窗口的交互实现

| 需求 | 实现 |
|---|---|
| 可拖动 | `WM_NCHITTEST` 在标题栏区域返回 `HTCAPTION`（系统拖，无拖影） |
| 可改大小 | 窗口保留 `WS_THICKFRAME`，`WM_NCHITTEST` 在边缘 8px 返回 `HTLEFT/HTRIGHT/...` |
| Win11 吸附布局 | 最大化按钮区域返回 `HTMAXBUTTON`，悬停弹出 Snap Layouts |

| 深色标题栏 | `DWMWA_USE_IMMERSIVE_DARK_MODE` |
| 缩放流畅 | 拖动全程完整重绘；`WM_SIZE` 主动 `InvalidateRect` 触发 `WM_PAINT` 绘制（铁律 7 修订版） |

## 7. 图标与内存预算

128px 基准、且支持 `Ctrl+滚轮` 缩放，若把全部图标按最大尺寸常驻，内存会失控
（139 条 × 256px × 4B ≈ 36MB）。因此采用三层控制：

1. **只加载可见方格**：内容区一屏通常 10~15 个方格，其余不提取图标；
2. **LRU 缓存 + 硬性预算上限**：超出预算淘汰最久未用的位图；
3. **缩放档位量化**：`Ctrl+滚轮` 在量化档位间跳（如 32/48/64/96/128/192/256），
   避免每个像素值都产生一份缓存。

按此设计，256px 下 15 个可见图标约 3.9MB，全库内存占用与条目数基本解耦。

### 7.1 实测数据（`quick-spin --selftest`，空面板、无图标）

| 阶段 | 私有提交 | 说明 |
|---|---|---|
| 进程基线（尚未建窗口） | 1.5 MB | 几乎为空 |
| 建窗口 + D3D11/D2D1/DComp 设备 | **+41.9 MB** | 远高于最初估算，见下 |
| 绘制第一帧 | +4.3 MB | 渐变笔刷、资源创建 |
| **空载合计** | **约 47.6 MB**（工作集 33.0 MB） | |

**最初估算 15~35 MB 偏乐观，实测翻倍。** 主要成本在 D3D11 设备创建 ——
它会连带加载 d3d11 / dxgi / d2d1 / dwmapi 等 DLL，并产生驱动侧分配。
这部分是"用 GPU 合成换取零拖影、零闪烁"的固定门票，不随条目数增长。

图标缓存是后续唯一会显著增长的部分（上限 24 MB），
因此**带上图标后的稳态目标应修正为 45~70 MB**，而不是原来的 15~35 MB。

若这个量级不可接受，可退回到"分层窗口 + 软件绘制"路线把内存压到 15 MB 以内，
代价是拖动必然出现残影 —— 与本项目"不得有拖影闪烁"的硬约束直接冲突，
因此不推荐。

### 7.2 测量口径提醒

任务管理器默认"内存"列是**私有工作集**，需要遍历驻留页逐页判断是否共享才能算出；
`--selftest` 目前给的是**私有提交量**（对应"提交大小"列）与工作集。
要核对"内存"列，在程序运行时执行：

```powershell
Get-Counter "\Process(quick-spin)\Working Set - Private"
```

多窗口（弹出新窗口）的取舍，**共用什么、不共用什么是分开决定的**：

* **共用**同一个 D3D11 设备与同一个 UI 线程 —— 每个窗口只多一条 SwapChain
  与一个 DComp Target，增量约 1~2 MB；
* **不共用**图标管线：每个弹出窗口有自己的加载线程与位图缓存
  （见 `src/popout/icons.rs`，位图缓存上限 8 MB/窗口）。

为什么图标缓存不共用：共享就要把主窗口的 `&mut` 拿到另一个窗口的绘制路径里用，
于是要么引入 `RefCell`、要么面对借用别名 —— 两条路都把"谁在什么时候动缓存"
变成隐式约定，而症状是"偶尔画错一张"这类极难定位的问题。
代价是每个窗口多一条加载线程与一份缓存，已在需求上确认接受。

**单个弹出窗口的内存量级**：

**实测**（使用者，2026-10-18，任务管理器口径，图标 48px）：
**每多开一个弹出窗口约 +4.5 MB。**

下面这张表是**按代码推算的分项**。注意它**只覆盖"图标管线"这一半**，
窗口与图形资源不在表里 —— 这正是两者对不上的原因（见下）：

| 项 | 用户当前设置（图标 48px） | 极端设置（图标 256px） |
|---|---|---|
| 位图缓存（`POPOUT_BUDGET` 封顶） | ~0.3 MB | 上限 8 MB |
| 加载线程的原始像素备忘（每窗口最多 64 条） | ~0.6 MB | 上限 ~16 MB（需要曾请求过 64 个不同条目） |
| 线程栈（保留量，实际提交少得多） | ~1 MB | ~1 MB |

一屏能显示的图标总量几乎恒定（方格随图标一起变大，能放的格子就变少），
所以"位图缓存"这一项很小；**大图标尺寸下的主导项是加载线程那份备忘**。
如果用户把图标调到 256px 并且开了多个窗口，需要重新评估，可选做法是给弹出
窗口的 `Loader` 一个更小的 `WORKER_MEMO`。

**不要拿这张表当"一个窗口的总量"。** 实测 4.5 MB 比表内合计明显更大，
差额来自本节开头那一条本身（每条 SwapChain + DComp Target 增量 1~2 MB）、
线程栈的**保留量**（表里那 1 MB 是保留，任务管理器看到的未必同样是这个数）、
以及窗口自身的 D2D/D3D 资源。教训是：分项推算能说明"哪一项会随什么增长"，
但**不能替代总量实测** —— 这张表原先写着"当前设置下每个窗口不到 1 MB"，
与实测差了 4 倍多。

两个窗口的图标一致**不靠共享状态**，靠同一套规则：图标来源只有一处
（`App::icon_source`：更换图标优先，否则用 `.lnk` 本身），
键的构造只有一处（`IconSource::key` + `pixel_size`），两边都走它。

## 9. 条目操作的设计更正（2026-10-17）

### 9.1 结论：全部是**程序内元数据覆盖**，不动来源文件

需求原话：**"删除图标只是删除本程序里的，不删除来源"**。

初版实现走反了方向 —— 把"删除"做成了 `SHFileOperationW` 把 `.lnk` 送进回收站。
那是**破坏性**操作，而且顺着这个思路，重命名要改文件名、更换图标要改写 `.lnk`
（`IShellLinkW` 的 Load/Save 顺序一旦写错就会清空快捷方式的目标与参数）、
移动到要移动文件 —— 整条链都在动用户的文件，任何一处出错都不可逆。

更正后的统一模型：**程序维护一份"按 `.lnk` 路径索引的覆盖表"，只影响本程序显示。**

| 菜单项 | 不做什么 | 做什么 |
|---|---|---|
| 打开位置 | — | `explorer /select,` 打开所在文件夹（只读操作） |
| 删除 | **不删文件** | 覆盖表里标记隐藏 |
| 重命名 | **不改文件名** | 覆盖表里存显示别名 |
| 更换图标 | **不写 `.lnk`** | 覆盖表里存图标路径覆盖 |
| 移动到 | **不移文件** | 覆盖表里改所在分组（选项卡） |

好处：

* 全部操作可逆 —— 清掉覆盖表就恢复原样，不需要回收站
* 不碰 `.lnk` 二进制格式，`IShellLinkW` 的"先 Load 再 Save"陷阱直接消失
* 覆盖表存 `state.toml`（程序自己的文件），不重写用户的 `config.toml`

### 9.2 覆盖表的键与失效

键用 `.lnk` 的**完整路径**。已知取舍：用户若在资源管理器里移动或改名该文件，
覆盖记录会失配（表现为"隐藏的条目又冒出来了"）。不自动跟随改名 ——
按路径匹配是确定的，跟随需要跟踪文件 ID，代价远大于收益。

### 9.4 "移动到"的确切语义（2026-10-17 确认）

需求原话：**"只是本程序内部的快捷方式，移动到其他选项卡或者主界面"**。

所以"移动到"是**程序内分组**，不是移动磁盘上的文件：

* 覆盖表里存一个 `group: Option<String>`（目标选项卡的 key）；
  `None` 表示"跟来源走"，即按扫描出来的 `Origin` 归入默认选项卡。
* 二级菜单列出**现有选项卡**（读 `cfg.tabs`）。主界面**就是其中一个普通选项卡**
  （key 为 `MAIN_TAB` = `"main"`），**不是"显示全部"的视图** —— 按需求它和别的
  选项卡一样，只显示自己的条目。覆盖表里 `group = None` 只是**回落到主界面**。
* 当前所在的分组要在二级菜单里**标注出来**（打勾或置灰），
  否则用户不知道"移动"有没有生效。

与"不删来源"原则的一致性：整个操作只改 `state.toml` 里的一行，
用户的 `.lnk` 和文件系统完全不受影响，随时可撤销。

### 9.5 覆盖表的字段汇总

| 字段 | 类型 | 作用 |
|---|---|---|
| `hidden` | `bool` | 删除（仅本程序隐藏） |
| `alias` | `Option<String>` | 重命名（显示别名） |
| `icon` | `Option<PathBuf>` | 更换图标（显示用图标文件） |
| `group` | `Option<String>` | 移动到（目标选项卡 key；`None` = **回落**主界面 `MAIN_TAB`） |
| `order` | `Option<u32>` | 显示顺序（拖动排序写入；`None` = 从未排过序，见 §13） |

键是 `.lnk` 的完整路径。空覆盖（五个字段都是默认值）应当从表里移除，
避免 `state.toml` 越积越长。


侧栏选项卡的"删除"在**该选项卡下还有条目时不可用**（需求原话："有内容时无法删除"）。
用 `Library::view(&tab, "")` 取条目数，非零即置灰，并显示置灰原因 ——
只置灰不给原因，用户只会认为"点了没反应"。

## 11. 条目模型改为"手动添加"（2026-10-17）

### 11.1 需求与结论

需求原话：**"默认保留一个主窗口按钮。自动扫描先不做，目前只做全部手动添加。拖入就复制一个快捷方式进来。"**

这改变了程序的定位：从**"扫描系统、自动归类"**变成**"空白起步、手动编组"**。

| | 旧 | 新 |
|---|---|---|
| 条目来源 | 扫描开始菜单 / 桌面 | 程序自己的 `%APPDATA%\QuickSpin\shortcuts` |
| 默认选项卡 | 全部 / 程序 / 桌面 | **只有「主窗口」一个** |
| 归属判断 | 按 `Origin` 自动归类 | **只看覆盖表的 `group`**，未指定归主窗口 |
| 添加方式 | 自动 | 拖入 `.lnk`，**复制**一份进来 |

### 11.2 为什么拖入是"复制"而不是"引用"

复制到程序目录，代价是磁盘上多一份几 KB 的 `.lnk`；换来的是**原文件被移动、改名、删除后条目不失效**，程序数据自包含。

只接受 `.lnk`：拖进来一个 exe 或图片并不是"添加条目"的意图，**静默忽略**比自作主张地替用户生成快捷方式更安全（后者会改动用户的文件布局）。

同名不覆盖，自动加 `(2)`、`(3)` 序号 —— 直接覆盖会让"拖两次同一个快捷方式"丢掉第一条。

### 11.3 拖放其实是**两条**路径，真正干活的是 OLE 那条（2026-10-18 更正）

本节原来的说法是"用老式的 `WM_DROPFILES`，实现 `IDropTarget` 收益几乎为零"。
**那个判断是错的，而且它直接掩盖了一个 bug。**

窗口实际装了两套接收：

| 路径 | 入口 | 能收到什么 |
|---|---|---|
| `WM_DROPFILES` | `DragAcceptFiles` | 只有文件系统路径（`CF_HDROP`） |
| OLE `IDropTarget` | `RegisterDragDrop` | 壳命名空间项（此电脑、回收站…）**以及文件** |

壳命名空间项没有文件路径，`WM_DROPFILES` **一个字都收不到**，症状是"拖上去毫无
反应、也不报错"。所以 OLE 目标不是"收益几乎为零"，而是**必须有**。

后果是：**资源管理器拖动本身就是 OLE 拖动**，注册之后文件拖入也先到 OLE 那条路。
也就是说 `WM_DROPFILES` 在实际使用中基本收不到东西 —— 真正处理拖入的是
`platform::drop_target`。

两条路的分工必须记住，否则同一个 bug 会重演：

* `drop_target` **只负责落盘**（把拖进来的东西变成我们目录下的 `.lnk`），
  再把落盘的路径攒起来、发一个"有新东西了"的消息。它看不到界面状态，
  **不知道当前选中哪个选项卡**。
* **归属必须由 `App` 决定**：取走那些路径，登记成"当前选项卡"，然后重新扫描。

曾经 `ExternalDrop` 那里只有一句 `rescan()`，注释还写着"归属分组也由那边按当前
选项卡登记过了"——**那边从来没有分组逻辑**。于是拖进来的条目永远没有分组，
按 `Library::view` 的回落规则全部进了主界面，**在哪个页面拖入都一样**。
那句注释比 bug 本身更坏：它让人不再去看那边的代码。

由此立一条**前提**：往覆盖表里写条目之前，文件必须**已经在快捷方式目录里**。
两条路都满足（复制完才登记 / 落完盘才发消息），登记完立刻 `save()`。

### 11.4 就地编辑重命名

需求原话：**"重命名不要弹出窗口了，就在把文字部分变为可编辑框，输入后回车或者点击其他地方确认就行了"**，且**"编辑时候临时加宽"**。

弹窗方案（`platform/text_input.rs`）已整体移除。它有个绕不过去的问题：**原生 Win32 对话框永远无法和自绘界面真正统一** —— 标题栏是系统的、按钮样式不可配、边框不可控。逐项修补（深色标题栏、自绘按钮、深色输入框）只是让它"没那么不像"，而不是"像"。

就地编辑还有一个前提：**窗口层必须有键盘事件管道**。这也是「Esc 关闭右键菜单」一直欠着的原因，两者一并解决。

**按 char 而不是按字节操作**：`String::insert`/`remove` 接受的是字节索引。中文一个字符占 3 字节，按字节切光标位置会切断字符——轻则乱码，重则 panic。所有光标移动与删除都必须经 `char_indices()` 换算。

提交时机有三个：回车、点击别处、失去焦点。**点击别处要先提交再继续处理这次点击**，不能吞掉它。空文本等于清除别名（回退原名），不存空字符串。

### 11.5 覆盖表清理的判据：文件在不在，而不是"这轮扫描有没有收录"

`prune_overrides` 清的是**孤儿记录**。判据一度写成"本轮扫描结果里没有这个键就删"，
这与"文件真的没了"**不等价**，差别正是几个 bug 的来源：

* 扫描是异步的。一次在拖入**之前**开始、拖入**之后**才回来的扫描，它的列表里
  没有刚复制的文件 —— 刚登记的归属会被这轮清理当孤儿删掉（条目突然消失，
  下次扫描再出现时已经回落到主界面）。
* 目标临时不可用的条目（U 盘拔了）会被扫描判为失效而**不收录**，
  但它不该因此丢掉用户设置过的隐藏 / 改名 / 分组。

现在判据是 `live.contains(key) || Path::new(key).is_file()`。目录里通常几十个条目，
每条一次 `metadata` 是微秒级，而扫描本身是低频操作 ——
这点代价换"清理不会误伤"是划算的。

## 13. 条目排序与拖动重排（2026-10-18）

需求原话：**"新快捷方式自动放到末尾"**、**"拖动可以改变图标排位"**。

### 13.1 排序规则：两档而不是一档

`EntryOverride.order` 是 `Option<u32>`，`None` 表示"从未被排过序"。
`Library::view` 的排序键是 **`(order.is_some(), order.unwrap_or(0))`**：

| 档 | 含义 | 排在哪 |
|---|---|---|
| `None` | 老条目（拖动排序之前就存在） | 前面，按扫描顺序 |
| `Some(n)` | 显式排过序的条目 | 后面，按 `n` 升序 |

`sort_by_key` 是**稳定**排序，所以 `None` 那一档保持扫描顺序 ——
加排序这一件事本身不会打乱用户现有的排列。

**为什么两档而不是一档**：新条目的序号取"现有最大值 + 1"。若让 `None` 直接
当 0 参与比较，第一个新条目的序号 1 会插到所有老条目**前面**去。分成两档
才能保证"新加的永远在末尾"。

### 13.2 拖动排序必须先物化整张表

用户把第 3 条拖到第 1 条前面时，若只给这一条写 `order`，它会因为"有 `order`
的排在无 `order` 的后面"直接甩到**末尾** —— 看起来就像功能坏了。

所以 `App::apply_reorder` 先把当前选项卡内**全部**条目按当前视觉顺序落成
`0..n-1` 的显式序号，再挪被拖的那一条（先摘除、再插入；摘除之后目标位置
若原本在它后面，要整体前移一格）。位置没变时**不写盘**。

物化**只覆盖当前选项卡**：`Library::view` 先按选项卡过滤再排序，
不同选项卡的序号永远不参与同一次比较，各自独立编号是安全的。
顺带的好处是"动一个图标"不会把别的选项卡也写进状态文件。

基准视图用**不带搜索词**的那一份。搜索时可见集合只是它的一个子序列；
若拿搜索结果去编号，没被搜到的条目会继续保持 `None`，于是清空搜索框的
那一刻它们整体跳到最前面 —— 看起来像排列被打乱了。

### 13.3 落点与反馈

`Layout::drop_slot_at` 把鼠标位置换算成"第几道缝"（与 `tile_at` 同口径，
返回条目下标 `0..=len`）：

* 落在某个方格上：按**中线**分前后（左半 = 插在它前面，右半 = 插在它后面）；
* 落在方格之间、行尾、最后一格右边的空白：取**最近的方格中心**再分前后。
  少了这一支，"拖到最后一个图标右边"就算不出落点，而那是最常用的操作之一
  （把条目挪到末尾）；
* 点不在内容区里一律返回 `None`（拖到侧栏/标题栏/窗口外 = 放弃这次拖动）。

拖拽期间在网格里画一条 2px 强调色竖线标出这道缝（`GridPainter::draw` 的
`drop_slot` 参数）。**落点与选项卡高亮互斥**：鼠标要么在选项卡上（改分组），
要么在网格里（改排序），不会同时成立。

### 13.4 已知限制

* **拖拽期间没有自动滚动**：要跨屏搬运只能先滚动、再拖。条目一屏放得下时
  没有影响；加上它需要引入定时器与"拖到边缘持续滚动"的状态机，
  与"不闪烁、不卡顿"的目标相冲，先不做。
* 顺序按选项卡独立编号，跨选项卡**没有**全局顺序。这是刻意的：
  `view` 先过滤后排序，跨选项卡的序号本来就不会被放在一起比较。
* `state.toml` 里 `[entries.*]` 各小节的**书写顺序**每次保存都可能不同
  （`AppState::entries` 是 `HashMap`，迭代顺序每个进程都不一样）。
  内容不变，只有字节序会变。

## 14. 可执行文件是 GUI 子系统（2026-10-18）

### 14.1 问题与结论

双击 exe 会弹出控制台黑框。根因不是配置，是 **PE 子系统**：
`Subsystem = 3`（`WINDOWS_CUI`）—— 源码里从来就没有 `windows_subsystem` 属性，
所以它一直是控制台程序，双击必然得到一个控制台。

修法是一行：`#![windows_subsystem = "windows"]`（变成 `Subsystem = 2`）。

对**这个程序**而言这不是可选项：它常驻托盘、支持"启动后自动收起"，
跟着一个关不掉的黑框与产品定位直接冲突。

### 14.2 代价与处理

GUI 子系统的代价是进程默认**没有可用的标准句柄**，`println!` 无处可写。
两种模式分别接上（见 `main.rs` 的 `prepare_console`）：

| 模式 | 标准句柄接到 |
|---|---|
| 命令行（`--selftest` / `--diagnose` / `--open` / `--help`） | 父进程的控制台；父进程没有才 `AllocConsole` |
| 图形界面（无参数 / `--gui`） | `NUL` |

三条必须同时做到，少一条就出问题：

1. **已经拿到有效标准输出时什么都不做。** 那说明输出被重定向到了管道或文件
   （`quick-spin --diagnose | findstr ...`），覆盖成 `CONOUT$` 会把管道打断。
   判据是 `GetStdHandle(STD_OUTPUT_HANDLE).is_ok()`。
2. **图形界面模式必须把 stdout/stderr 接到 `NUL`。** 这一条看着像洁癖，其实是
   稳定性要求：Rust 的 `print_to` 在写入失败时会 `panic!`，而本工程
   `panic = "abort"` —— 一句"写不出去的日志"会把整个界面**直接终止**，
   而且不留任何痕迹。接到 `NUL` 后写入永远成功。
3. **句柄要故意泄漏（`mem::forget`）。** `File` 一 drop 就关掉句柄，
   标准输出随即变成野句柄，之后每一次 `println!` 都会失败。

第 1 条依赖的语义已核实：windows-rs 的 `HANDLE::is_invalid()` 把 **`-1` 和 `NULL`
都判为无效**，所以双击启动（stdout 为 NULL）时 `GetStdHandle` 返回 `Err`，
一定会走到绑定那一支：

```rust
pub fn is_invalid(&self) -> bool { self.0 == -1 as _ || self.0 == 0 as _ }
```

### 14.3 已知取舍：shell 不会等待 GUI 程序

`cmd` / PowerShell 对 GUI 子系统的程序**不等待**，所以直接敲
`.\quick-spin.exe --diagnose` 会立刻回到提示符，输出在提示符之后才刷出来，
`$LASTEXITCODE` 也拿不到。要等待、要退出码、要管道，就用：

```powershell
cargo run --release -- --diagnose                  # cargo 会等
cmd /c "target\release\quick-spin.exe --selftest"  # cmd 会等
Start-Process -Wait -PassThru ...                  # 显式等待，可读 ExitCode
```

这是子系统带来的、**在进程内无法消除**的后果（等不等由父 shell 在启动时决定，
子进程改不了）。要同时满足"双击无黑框"和"命令行体验完整"，标准做法是拆成两个
可执行文件（GUI 的 `quick-spin.exe` + 控制台的 `quick-spin-cli.exe`），
但需要先把工程拆出 lib。当前三条命令行用途（自检、诊断、按名启动）都够用，
所以先不拆。

## 15. 多选与框选（2026-10-18）

需求原话：**"当前多选后点击空白位置不会取消选择，修改为点击空白取消选择。
增加按住空白拖拽框多选图标功能。"**

### 15.1 点击空白取消选择

落在 `App::on_mouse_down` 的**最后一条分支**：所有控件（方格、选项卡、
标题栏按钮、设置按钮、菜单项、标题文字）都没命中，就是"空白处"。

**按下即清，不是等松手。** 这是资源管理器的语义，也让框选一开始就能看到
"从空白开始重选"。按下时还要返回 `true` 请求重绘，否则方格上的选中态要等到
下一次鼠标移动才顺带消失，看着像"点了空白没反应"。

按着 **Ctrl** 则不清：那是"在现有选择上追加"，清掉就变成替换了。

### 15.2 框选

从空白处按下并拖动就拉出选框。三条定则：

1. **只在网格内容区起框**（`layout.content`）。侧栏空白处、标题栏下沿拖拽
   不拉框 —— 那里没有方格可选，拉出来的框只会盖住界面。
   但**清空选择**在上面那两处照样生效（它们是"空白处"）。
2. **每帧从基线重算**，而不是往选中集里追加。`Marquee::base` 是按下那一刻的
   选中集，每一帧的 `selected` 都是「`base` ∪ 框内条目」。
   追加的话框划过再划回来，格子会一直亮着，没法"取消划中" ——
   而所见即所得正是框选唯一的价值。`base` 也顺带承担了 Ctrl 的语义。
3. **判交用相交，不是包含**（`RectI::intersects`）。用户只要划到方格的一角就
   该选中它；要求整个方格被框住的话，方格和图标一样大，随手一划几乎选不中。
   注意是**半开区间**比较：恰好相切的两条不算相交，而宽或高为 0 的线状框
   依然有效（纯竖直/水平拖动也要能选中）。

`MARQUEE_MIN = 3px`：位移不到它就算"点了一下"，**不**当框选处理。
没有这个阈值的话，在方格之间点一下，那个 0×0 的框会和紧邻的方格相切，
于是"点空白"顺带选中了旁边一条，用户会觉得莫名其妙。

### 15.3 已知限制（与方格拖拽同源）

* **没有 `SetCapture`**：鼠标移出窗口就收不到 `WM_LBUTTONUP`。所以
  `Event::MouseLeave` 与下一次按下都会取消框选 —— 不取消的话，选框会跟着
  光标在窗口外乱飘，下一次松手还会按**过期的几何**去选条目。
* **没有自动滚动**：框选只能选到当前可见的那几行。要选到屏幕外的条目，
  得先滚动再框。加上它需要定时器与"贴着边缘持续滚动"的状态机，
  与"不闪烁不卡顿"的目标相冲，先不做。
* 选框绘制时自己再压一次内容区裁剪（`GridPainter::draw_marquee`）：
  选框能拖到侧栏上去，不裁剪会在侧栏上画出一条半透明带子。

## 16. 描边方向改为按亮度自动切换（2026-10-18）

原规则出自设计需求："**边框统一为同色系更深色**"，实现是
`panel_base.darken(0.35)`。

这条规则在浅色面板上没问题，但在**深色面板上自我抵消**：面板本来就接近黑，
再压暗 35% 仍然接近黑，边框与面板分不开 —— 等于没有边框。实测数据
（"差"取**最大单通道差**；面板色是派生描边用的那个中点，
不是 `--diagnose` 打印的渐变两端）：

| 底层色 | 面板（派生中点） | 亮度 | 旧描边 | 差 | 新描边 | 差 |
|---|---|---|---|---|---|---|
| `#000000` | `#080808` | 0.03 | `#050505` | **3** | `#5E5E5E` | **86** |
| `#1E0A2E` | `#241133` | 0.09 | `#170B21` | **18** | `#71647A` | **83** |
| `#84A845` | `#84A649` | 0.60 | `#566C2F` | 58 | `#566C2F` | 58 |
| `#F2F4F7` | `#EBEDF0` | 0.93 | `#999A9C` | 84 | `#999A9C` | 84 |

浅色两行的新旧值完全相同 —— 行为没变；深色两行从"几乎看不见"（差 3、18）
变成清楚可见（差 86、83）。纯黑底尤其极端：旧描边 `#050505` 落在 `#080808`
的面板上，差 3 个色阶，肉眼等于没有。

所以方向改为**按面板亮度选：浅底往深、深底往浅**（阈值 0.5）。

要点：**"和面板拉开差距"才是目的，"更深"只是达成它的手段之一。**
把手段当成规则，就会在深色底上得到一条看不见的边框。
浅色底的行为完全不变（差值列相同），只有深色底被修正。

`border` 与 `tab_active_border` 仍然共用同一个派生色 —— 它们出现在相邻位置，
色相一多，交界处就会互相打架。这一点没有变。

## 17. 弹出子窗口（2026-10-18）

从侧栏选项卡的右键菜单打开一个**独立顶层窗口**，显示该选项卡的内容。
需求原话："弹出只是多了一种显示方式，并不影响本身在主窗口的内容。"
所以它不把选项卡从侧栏拿走，两边是同一份数据的两个视图。

### 17.1 每个窗口自给自足

弹窗有自己的 `Renderer`/`Composer`/`Painter`/`TextEngine`，**以及自己的图标
加载线程与位图缓存**（`src/popout/icons.rs`，方案 A）。

不共享主窗口那一份的理由不是省事与否，而是**借用**：共享就要在"另一个窗口的
绘制路径"里拿到主窗口的 `&mut`，于是要么引入 `RefCell`、要么面对借用别名 ——
两条路都把"谁在什么时候动缓存"变成隐式约定，症状是"偶尔画错一张"这类极难
定位的问题。代价是每窗口多一条加载线程 + 一份缓存，实测约 **+4.5 MB/窗口**
（口径与分项见 §7.2）。

**两个窗口的图标一致靠"同一套规则"，不靠共享状态**：图标来源只有一处
（`App::icon_source`）、键的构造只有一处（`IconSource::key` + `pixel_size`）、
显示名只有一处（`library::display_name`：别名优先，否则原名）。这三处都曾经
因为"两处各写一份"而出过 bug —— "弹窗里的名字改不掉"就是其一。

### 17.2 三条与窗口生命周期有关的铁律

这三条都是**崩溃过**才总结出来的，不是预防性设计：

1. **处理器以裸指针存在窗口上下文里 ⇒ 拥有者必须装箱。**
   `Window` 的 `GWLP_USERDATA` 存的是 `*mut dyn Handler`。若把处理器先
   `attach` 到窗口、再 `Box::new` 搬进容器，裸指针指向的就是**栈上那个已经
   失效的地址** —— 第一次绘制即崩溃。正确顺序是**先装箱、后 attach**。
   同理，容器扩容会搬动元素，所以任何被窗口指着的对象都不能放在容器里。
2. **一个线程只能有一个消息循环。** 主窗口跑 `message_loop`；第二个窗口
   不能自己再跑一个（同一线程两个循环会互相抢消息）。所以后建的窗口走
   `Window::attach_ptr`，只挂处理器，循环仍由主窗口那个跑。
3. **关闭是异步的，不能当场释放。** `close()` 只是 `PostMessage(WM_CLOSE)`，
   窗口这一刻还活着，而窗口过程仍会用到那个裸指针。曾经在
   `toggle_popout` 里"先 `remove` 再从表里消失"，等于当场释放 `Box` ——
   等 `WM_CLOSE` 被处理时就是悬垂指针。现在**只请求关闭**，释放交给收尾点
   （那时窗口真的没了）。

### 17.3 关闭：两条路收敛成一条

关闭有两条路，但只有一条会回到装配层：菜单（装配层发起的，它知道）与
**弹窗自己右上角的 ✕ / Alt+F4**（窗口层销毁自己，装配层不知道）。

后者会让 `App::popouts` 里留着一个死窗口：右键菜单的文案是按"表里有没有"
生成的，于是仍然显示「关闭子窗口」（点下去毫无反应），`state` 里的 `open`
也还是 `true` —— 下次启动会把一个用户已经关掉的窗口恢复出来。

解法是**回报通道**（`src/popout/report.rs`）：窗口层在**销毁时**把选项卡 key
攒进静态缓冲，装配层在明确的收尾点取走。

* 放在销毁时而不是 `on_close_request`：后者只有走 `WM_CLOSE` 才触发，
  而销毁覆盖**所有**路径。
* **刻意不做每帧存活探测**（`IsWindow`）：那是"每帧 N 次 syscall"，而且把
  "谁关了"变成轮询推断 —— 查到窗口没了，还得再猜是哪一个。
* 同一个问题在 `platform::drop_target` 那里已经解过一次（拖放目标落完盘，
  把路径攒进静态缓冲等上层取走）。两处刻意长得一样，见到第三处不用重新想。

### 17.4 状态归属：窗口层不写 `state.toml`

弹窗的几何 / 吸附 / 钉住状态都归装配层管。窗口层只**回报**"我变了"
（`report_changed`），为什么：

* 让窗口层直接写状态，"谁负责落盘"就变成两处，且窗口层还得知道 `state` 的形状；
* 回报通道与"已关闭"**分成两条**：两者的收尾动作完全不同（一条要摘表项、
  一条只更新记录），合成一条还得让上层先分辨是哪一种。

落盘点两处、**都不是每帧**：收到回报时、以及 `save_state` 里兜一次
（用户拖完弹窗、没有任何后续动作就直接退出程序 —— 那时只有后者会写）。

`persist_popout` **只写它该写的那部分**：`name` 与 `base_color` 保留记录里的值。
弹窗自己那份是默认值，整体回写会把用户起的名字和配色抹掉。

### 17.5 吸附跟随：事件驱动，且判据不能靠猜

* 驱动是主窗口的 `WM_MOVE` / `WM_SIZE`（新增 `Event::Moved`）。
  **没有轮询定时器。** `WM_MOVE` 在拖动时是每帧来的，所以看起来是连续跟随。
* `Event::Moved` **刻意不带坐标**：`WM_MOVE` 的 lParam 是 16 位，超宽虚拟桌面
  会被截断成负数；消费方本来就要拿完整矩形，带一份可能被截断的坐标只会变成陷阱。
* `WM_MOVE` **不标脏**：只是挪了位置，内容一个像素都没变，标脏会让拖动过程中
  每个 `WM_MOVE` 都白重画一帧。
* `Window::move_to` 用 `SWP_NOSIZE | SWP_NOZORDER | SWP_NOACTIVATE`：
  不产生 resize、不改 Z 序（否则跟随会把主窗口压到下面）、**不抢焦点**
  （否则主窗口每移动一次焦点就跳到弹窗上）。

**怎么区分"用户拖动"与"程序吸附"**（这一步最容易做坏的地方）：用
**`WM_ENTERSIZEMOVE` / `WM_EXITSIZEMOVE`**。这两个消息只有系统进入模态
移动/缩放循环时才会发 —— 只有用户真的抓住标题栏或边框才会来；程序自己调
`SetWindowPos` **不会**产生它们。所以判据是"只在用户拖完之后比较几何"，
程序摆的那些从来没进过这一段，不可能被误判。

否掉另外两种做法：**时间窗口**是拿时序猜；**标志位**一旦漏配对（异常路径、
嵌套拖动）就会让窗口莫名其妙脱离吸附，而且查不出来。

顺带区分了移动与缩放：位置变了 = 用户在移动它 → 脱离吸附；**只有尺寸变了 =
用户在缩放它 → 保持吸附**并记下新尺寸。

### 17.6 "钉住"的语义（已被使用者收窄，**不要再引入 WorkerW**）

原设计是把窗口 `SetParent` 到桌面的 `WorkerW`（常驻最底层、不可移动）。
使用者 2026-10-18 放弃了它：

> "不用 WorkerW 留在桌面，按照普通窗口处理就行。钉的作用就只是留在桌面
> 不随主体最小化。"

所以**钉住只有一件事：主窗口最小化/隐藏到托盘时它不跟着隐藏**。
它就是一个普通顶层窗口：普通 Z 序、可拖动、可缩放。

后果是 `pinned` 与 `docked` **正交**：`docked` 管位置（跟着主窗口摆），
`pinned` 管可见性（主窗口收起时留不留着）。`normalize` 里原先那条
`if pinned { docked = false }` 已删除 —— 它当年的依据是"钉 = 常驻桌面层"，
而且会**静默改写用户的记录**（手改成两者都为真时，一次 `normalize` 就把
`docked` 抹掉，表现为"我明明没拖它，怎么就不吸附了"）。

**所有显隐都必须走 `App::set_main_visible`**（它顺带同步弹窗）。早先各处
各自调 `window.hide()`，而弹窗联动是后加的 —— 漏掉任何一处，症状就是
"主窗口收进托盘了，未钉住的弹窗还孤零零挂在桌面上"。

### 17.7 吸附数学只有一处

`src/popout/dock.rs` 是一个**纯函数**：输入主窗口矩形、弹窗尺寸、期望的侧、
显示器工作区、**已排在链上的窗口矩形**、**这个窗口当前在哪**，输出落位。
没有 HWND、没有 `windows` 类型。

* 它在**两个地方**要用（创建弹窗时第一次摆位、主窗口移动时跟随），
  两处各写一份必然漂移 —— 创建路径原先内联在 `App::toggle_popout` 里，现已改掉。
* 纯函数才能被 `--selftest` 完全覆盖（见 §17.8）。
* `dock_side` 存的是**用户期望的侧**，翻边只影响结果，不改那个意图。
* `clamp()` 主动避开标准库 `i32::clamp` 在 `min > max` 时的 panic ——
  弹窗比工作区还宽是真会发生的（窗口拉得比屏幕大，或工作区被竖排任务栏切窄）。

#### 17.7.1 多个窗口一起吸附：堆叠成链（2026-10-18 修）

原先每个吸附中的窗口都算**同一个位置**（右吸附 = 贴主窗口右边缘 + 上边对齐），
计算里**没有"那一侧已经站了别人"这个概念** —— 于是多个窗口一起吸附时
**完全重叠**（使用者实测报障）。这个 bug 不会被任何"看起来正常"的迹象暴露：
坐标是合法的，窗口也确实在吸附位上，只是都在同一处。

现在：

1. 沿主窗口那一侧**竖直排成一条链**：列 0 贴侧边、从主窗口上边缘起，
   遇到挡路的矩形就滑到它的下边缘 → **首尾相接**；
2. 一列排到工作区底边以下 → **另起一列**，x 往外挪，仍从主窗口上边缘起；
3. 链上被拖走留下的**空位会被回填** —— 判定就是"这里与所有已占用矩形都不相交"，
   **不需要另记一份空位表**（多一份状态就多一处会与真相不一致）；
4. **吸哪一侧**由这个窗口**当前中心**相对主窗口中心的方向决定（拖到哪边吸哪边），
   用中点而不是左边缘：窗口很宽时左边缘可能已在主窗口右侧，而它视觉上仍横跨主窗口；
5. 列间距取"自己与这一侧已占用矩形的**最大宽度**"：窗口宽度可能各不相同，
   固定间距会让宽窗口压到邻列（代价是最宽的窗口让新列多让开一档，刻意取舍）。

**输入为什么必须由装配层给**（`occupied`）：只有它持有 `popouts` 那张表。
纯函数保持纯 —— 它只知道几何，不知道谁是窗口。

**顺序上的关键**：`App::follow_popouts` 一趟走完、**边摆边累积** ——
每摆好一个就把矩形收进 `placed` 给下一个用。于是不必先扫一遍"别人的矩形"，
而且排在自己前面的已就位、后面的还没轮到，**自己不会挡自己**
（省掉"我要避开所有人，但包括不包括我自己"这类最容易写错的纠缠）。
顺序取自 `BTreeMap` 的键序，稳定不抖 —— 换成哈希或插入序会看到弹窗彼此跳。

**回填与"另起一列"都只由几何规则产生，没有专门的代码路径。** 这是有意的：
需求应当被规则消灭，而不是加分支去凑。

### 17.8 自检的边界：第二个窗口这条路覆盖不到

**必须先说清楚：`--selftest` 建不出第二个窗口。** 这条路径上的 bug 全部是
"0 error / 0 warning + 自检全绿"的状态下漏过去的，已经发生四次：

* 处理器裸指针指向栈地址 → 第一次绘制崩溃；
* 建了窗口但**漏了 `show()`** → 窗口根本不出现；
* 漏调 `TextEngine::ensure` → **标题与名称一个字都不显示**（`draw` 在笔刷
  为 `None` 时是**静默返回**的，既不报错也不留日志）；
* 关闭后菜单状态不同步。

所以：**绿色自检不是弹窗功能的交付证据。** 凡是"真的建出第二个窗口"才能
验证的行为，必须由使用者手动确认。

能自检的部分要尽量钉死，而且**要用具体期望值**，不要"全部通过"式的空断言：
吸附几何（满八个边界：两个方向的翻边、两侧都放不下、垂直夹紧、移动跟随、
超宽不 panic、无工作区不摆）、点击命中（格内 / 名称行 / 格间空隙 / 标题栏 /
四个按钮）、显示名规则、关闭回报语义、内容比较（改名 / 重排 / 改尺寸 /
换启动目标）、弹窗配色与"配色穿过落盘合并"、启动恢复集合。

**退出码必须反映实际结果。** 这一条是补出来的：自检的退出码曾经**恒为
`SUCCESS`**，于是"退出码 0"被当成了通过判据 —— 而一次反向验证（故意把
`merge_persisted` 改回旧规则）证明：自检报出两条失败并打印了实际值，**退出码
依然是 0**。凡是以退出码为判据的人（脚本、CI、以及后来的我）都会把红的看成绿的。

修法不是"记得同时看输出"，而是让判据只有**一个来源**：自检的每一行输出都走
同一个宏（`selftest_line!`），见到 `⚠` 就登记，函数末尾按登记数决定退出码。
**输出由谁产生，成败就由谁登记** —— 两个来源必然会脱节。

验证方式用**注入**而不是"改坏真实逻辑"：临时注入一行 `⚠` → 退出码 1；撤掉 →
退出码 0。比改坏真实逻辑安全，而且同样能证明断言链是通的。

### 17.9 "规则只有一处"的清单（弹窗带来的新增项）

| 规则 | 唯一出处 |
|---|---|
| 显示名（别名优先） | `model::library::display_name` |
| 图标来源（换图标优先） | `App::icon_source` |
| 缓存键（DIP→物理像素、按图/按图标） | `IconSource::key` + `icons::pixel_size` |
| 可见格数与格子几何 | `PopoutLayout::visible_tiles` / `tile_at` / `tile_index_at` |
| 吸附位置 | `popout::dock::dock_position` |
| 主窗口显隐 | `App::set_main_visible` |
| 启动一条 | `shell::launch::open_shortcut`（弹窗侧只是转发） |

每一条都对应一次真实的 bug 或一次险些发生的 bug。新增功能时若发现要"再写一份"
同样的规则，那基本就是要出问题的信号。

### 17.10 独立配色：色板与"用哪套"各自只有一处

每个弹窗可以有**自己的一套配色**（`PopoutWindow::base_color`，空串 = 跟随主窗口），
点标题栏的彩色四叶草弹出选色浮层。

* 候选色的唯一出处仍是 `config::theme::BASE_PALETTE`；解析与"色值 → 下标"也各只有
  一处（`theme::palette_colors()` / `theme::palette_index()`）。主窗口设置面板与弹窗
  浮层都调它们。**解析不了的颜色项要跳过而不是补默认色** —— 补了会让格子数与布局
  错位，表现是"点 A 却选中了 B"。
* **"下标 → 色值"也必须走同一条过滤**（`theme::palette_hex()`）。选色时是"格子下标
  → 写进状态的文本"，高亮时是"状态里的文本 → 格子下标"；直接拿格子下标去索引
  `BASE_PALETTE` 原表，会在有项解析失败时错位 —— 与上一条是同一个坑的另一面。
* `popout/palette.rs` 是**纯算术**（没有 HWND），所以浮层的几何与命中能完全被
  `--selftest` 覆盖。理由与 `dock.rs` 同源，而且这里更关键：§17.8 说了自检建不出
  第二个窗口，"浮层摆在哪、点到了哪一格"只能靠离线自检钉住。
* 浮层布局**算一次存下来**，绘制与命中共用同一份。两处各算一次就会出现
  "点中的和画出来的不是同一格"。窗口尺寸变化时重摆。
* `palette::resolve_scheme()` / `follows_main()` 是 `base_color` 语义的**唯一实现处**
  —— 创建、主窗口换色、用户选完色都走它。三个地方各写一次判断，迟早会出现
  "选了色但某一条路没跟上"。非法值回落到主窗口配色（状态文件是用户可手改的）。
* 弹窗同时留着主窗口的配色（`main_scheme`）：用户随时可能从"自己一套"切回
  "跟随主窗口"。有自己配色的窗口**不**受主窗口换色影响。

**落盘时的分工判据：`merge_persisted`（§17.11）。**

### 17.11 落盘合并：判据是"窗口层手里有没有这个值"

弹窗的状态（位置 / 尺寸 / 吸附 / 钉住 / 配色）都由窗口层持有权威值，落盘时与记录
合并。规则抽成纯函数 `PopoutWindow::merge_persisted(fresh, old)`，因此能被自检钉住
—— 这条规则出错的表现（"选了色、当时生效、**重启就没了**"）只有真的重启一次才会
暴露，属于最难查的一类。

| 字段 | 用谁的 | 为什么 |
|---|---|---|
| `name` | **记录里的** | 窗口层只有解析好的显示文字，拿不到原始的 `Option<String>`（"没设过"与"设成空"是两种意思），用窗口那份会把用户起的名字抹掉 |
| `base_color` | **窗口的** | 窗口层持有权威值：创建时从记录取，之后每次选色改它 |
| 位置 / 尺寸 / 吸附 / 钉住 | **窗口的** | 只有窗口自己知道 |

`base_color` 这一条曾经是反的：那时窗口回报的是默认值（`String::new()`），所以必须
保留记录里的值，否则用户设好的配色会被抹掉。**那条理由在窗口开始持有这个值之后
就消失了** —— 而继续保留会让用户新选的颜色被静默丢弃。记录这段是因为：**一条当时
正确的规则，会因为别处的变化而过时**，只写"现在改成用窗口的"，下一个人看不出
为什么，可能会因为"看起来更安全"又改回去。

### 17.12 启动时恢复

按 `state.popout.to_open()` 把上次开着的窗口开出来。两条约束：

* **复用同一条创建路径**：创建流程抽成 `App::open_popout(tab_key, show)`，菜单与
  启动恢复共用。再写一份"创建 + 摆位 + 装箱 + attach + show"迟早会漏掉其中一步
  —— 漏 `show()` 那一次的症状是"点了菜单什么都没出现"，而且不报错。
* **先按记录建出来（不显示），再决定显隐。** "要不要看得见"交给
  `set_main_visible` 那条唯一的显隐链判断，于是"启动时隐藏到托盘"这种情况
  不需要在这里再判一次 —— 多一处判断就多一个会漏的地方（漏了的表现是弹窗在
  托盘模式下自己冒出来）。

### 17.13 不在计划内 / 未接 / 已知待调

* 弹窗不支持拖动排序与多选。
* 未接 `hide_after_launch`：主窗口"启动后收起面板"开着时，从弹窗里启动**不隐藏弹窗**
  —— 弹窗是使用者主动开的独立视图，点一格通常意味着还要接着点下一格。这是使用者
  确认过的选择。
* ~~**已知外观问题：弹窗底部是圆角**~~ —— **已修**（2026-10-18，提交 `fa60eea`）。
  根因不是弹窗画错，而是它**从来没设过系统圆角偏好**（拿到 Win11 对顶层窗口的
  默认圆角），而面板半径又写死 `10.0`。现在系统偏好与面板半径同源于
  `Appearance::corner_style(outer_glass)`，见 §17.9 的"规则只有一处"。
* **已知布局边界**：选色浮层在**最小尺寸窗口**（200×160）里放不下 8×8 色板，

* **两个空配置项**：`appearance.system_round_corners` 与 `general.start_hidden`
  **全项目只出现在定义与默认值处，从未被读取**（界面上/文档上看起来有用，
  实际毫无作用）。**刻意没有擅自"修好"它们**——那会改变行为，属于要使用者拍板的
  事。见 §18.2。

## 18. 崩溃取证：让"程序突然没了"留下证据（2026-10-18）

### 18.1 为什么非做不可

使用者报告过一次崩溃。我当时查了三处，**全是空的**：

* `诊断.log` 没有崩溃行；
* `%LOCALAPPDATA%\CrashDumps` 里最新一份是几小时前的，**之后没有新转储**；
* Application 事件日志最近三小时**一条错误/警告都没有**。

原因不是"难查"，而是**根本没记**：

1. 本程序是 `panic = "abort"`（`Cargo.toml`），panic 信息走标准错误；
2. 而 GUI 子系统下标准错误被接到 `NUL`（见 `main.rs` 文件头）→ **消失**；
3. 而且当时**全项目没有 panic 钩子**（`set_hook` / `panic::` 零匹配）。

于是一次崩溃只留下一个现象："程序没了"。**分不清是正常退出还是崩。**

### 18.2 现在的取证设计

**panic 钩子**（`diag::install_panic_hook`，在 `main()` **第一件事**装上，
早于 `prepare_console` —— 于是参数解析、单实例、配置等各阶段的崩溃都覆盖，
命令行模式走同一个 `main` 也一并覆盖）。写进 `诊断.log` 三样：

    panic: <消息> @ <文件>:<行> （线程 <名字>）

* **payload 可能是 `&str` 也可能是 `String`**（`panic_any` 允许任意类型），
  所以两种都 downcast，都不是时用占位文本；
* **`文件:行` 是最有价值的一条** —— 它直接指向出问题的代码；
* **不做栈回溯**：发布版 `strip = "symbols"`，没有符号的回溯意义有限；
* **钩子自己绝不能 panic**（否则双重 panic）：不索引、不 unwrap，
  所有可能失败的分支都退化成占位文本；连 `log` 内部也是失败即返回。
* `panic = "abort"` 下钩子**仍会执行**（运行时先调钩子、再 abort），所以这条路通。

**生命周期锚点**（让"没了"能被分类）：

    主窗口已就位 hwnd=…
    窗口销毁: 主窗口（消息循环将结束）      ← 主窗口 → 循环要结束
    窗口销毁: 弹窗（消息循环继续）          ← 弹窗 → 程序**不该**退出
    窗口已彻底销毁 hwnd=…（存活 N）
    程序正常退出（消息循环结束）            ← 有它 = 正常；没有 = 崩了或被强杀

**判读规则**：日志停在"弹窗已关闭"之后、既没有主窗口销毁行也没有
"程序正常退出"行 → 那是崩溃（此时应当有 `panic:` 行）。缺 `panic:` 行而进程
也没了 → 被外部强杀（例如构建时 `Stop-Process`）。

**只在动作路径写**（创建 / 销毁 / 退出各一行），不每帧写 —— `diag::log` 每次
调用都会开文件追加，代价不高但不能滥用。

### 18.3 怎么验证钩子真的会写

**用注入，不改坏真实逻辑**：临时注入一句 `panic!` → 跑 → 确认日志出现
`panic: … @ 文件:行` 且进程退出码是 abort 的 `0xC0000409` → 撤掉注入、重建 →
确认 panic 行总数不再增加、自检恢复。

理由：**"装了钩子"和"钩子会写日志"是两件事**。这个工程已经吃过一次
"看起来绿其实是假绿"的亏（自检退出码曾经恒为 0），所以凡是"新加了一条通道"，
都要用一次能失败的实验证明它通。
